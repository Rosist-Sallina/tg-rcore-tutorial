# 任务三：扩展实验实践总结报告

## 一、与 AI 合作的实现过程

本次扩展实验共完成了四个游戏：ch3 贪吃蛇（图形版）、ch5 双人乒乓球、ch7 吃豆人、ch8 DOOM 移植。使用工具为 Codex CLI（GPT-5.4-xhigh）和 Claude Code（Claude Opus 4.6）。

### ch3：贪吃蛇（virtio-gpu 图形版）

在了解到仓库里有 `virtio-drivers` crate 可直接用之后，目标是"真图形但尽量简单"——QEMU 图形窗口显示，终端串口接收键盘输入。

AI 在设计阶段做了一个重要判断：当前 ch3 的用户态堆只有 16 KiB，放不下整帧缓冲（320x240x4 约 300KB），所以不能让用户态自己维护 framebuffer 然后整帧提交。正确做法是"内核持有 framebuffer，用户态只发绘图命令"。这直接影响了 syscall 的设计——新增了 `input_try_getchar`、`fb_info`、`fb_fill_rect`、`fb_present` 四个接口，而不是做一个"提交整帧"的 syscall。

实现过程中有一个容易忽视的问题：`w/a/s/d` 按键要求"按下立即生效，不需要回车"。这需要在 QEMU 启动时把终端设置成 raw 模式（`stty raw -echo`），让字符在用户按下后直接传到串口，不缓冲到换行。不做这一步游戏根本没法玩。

内核图形层只实现了三个原语（`clear`/`fill_rect`/`present`），越界裁剪在内核里做，用户态不需要担心溢出。每帧先清屏再整帧重绘，20x20 格子的贪吃蛇性能完全够用。

### ch5：双人乒乓球

这个任务的难点不是游戏逻辑，而是两件事的组合：把 ch3 的图形能力迁到 ch5（ch5 开了页表，MMIO 映射规则变了），以及在没有 ch7 pipe 的情况下做双进程协作。

ch3 的图形代码不能直接搬到 ch5，因为 ch5 引入地址空间之后，设备 MMIO 地址需要显式映射进内核页表，否则驱动读不到设备寄存器。这是迁移过程中花时间最多的地方——不是写新代码，而是把 ch3 那套驱动装进 ch5 的内核地址空间管理框架里。

双进程协作部分没有使用 ch7 的完整 pipe/fd 体系，只新增了最小 mailbox 三个 syscall（`mailbox_create`/`send`/`recv`），专门给 pong 用。设计思路是：子进程轮询串口，把方向键和退出事件发进 mailbox；主进程每帧 drain mailbox，取最后一次有效方向输入，推进物理状态，渲染整帧。

AI 提醒了一个工程细节：用 `pong` feature 隔离图形相关代码，保证默认的 `cargo run` 和 `./test.sh base/exercise` 完全不受影响。不做这个隔离的话，图形扩展会破坏原来章节的测例环境。

整个实现分成七步推进，每一步都有独立的验收点，上一步稳了再做下一步，整个过程没有出现"同时改了三件事然后不知道炸在哪"的情况。

### ch7：吃豆人

ch7 的主题是 pipe 和 signal，扩展任务的设计也把这两个特性实际用进去，而不是绕开它们。

最终方案：输入子进程通过 pipe 发送 `w/a/s/d/q` 单字节命令；暂停（P 键）和重开（R 键）通过 signal 控制，`SIGUSR1` 切换暂停/运行，`SIGUSR2` 在结束状态下触发整局重开。这个分工让 pipe 和 signal 都有实质性用途，不是摆设。

AI 建议分 10 个步骤来实现：先把"图形 + 输入"链路跑通，再做游戏本体（地图、移动、吃豆），再接 pipe，最后接 signal 和两只鬼。这个顺序的好处是图形链路和 ch7 内核特性（pipe/signal）是完全独立的两条线，互相不影响调试。

有一个实现细节值得记录：信号处理函数里只做两件事——设置 `AtomicBool` 标志位、调用 `sigreturn()`。真正的状态切换放在主循环里处理，不在信号处理函数里做复杂操作。这是为了避免信号处理函数的执行语境限制（不能安全持锁、不能安全分配内存等）。

鬼怪逻辑固定了两种策略：一只贪心追逐（选曼哈顿距离最小的方向），一只随机游走（有其他可选方向时不允许立刻反向）。一追一随机能制造出一种"被围堵"的紧迫感，比两只都追或都随机更有趣。

### ch8：DOOM 移植

这是四个游戏里工程量最大的一个。最后用的是 Claude Code 而不是 Codex CLI，因为这类大体量集成工作更需要在对话中保持长上下文。

DOOM 移植的核心不是游戏逻辑，而是平台适配层。`doomgeneric` 只需要五个平台函数：`DG_Init`（初始化）、`DG_DrawFrame`（刷帧）、`DG_SleepMs`（休眠）、`DG_GetTicksMs`（时间戳）、`DG_GetKey`（读键盘事件）。这五个函数背后对应内核的四个新 syscall（`framebuffer_init`/`framebuffer_flush`/`framebuffer_info`/`input_event`）。

与前几个游戏最大的不同是键盘输入。贪吃蛇/乒乓/吃豆人都用串口 UART 轮询读字符，但 DOOM 需要区分按键按下和释放（比如长按 W 前进），串口字符流做不到这个。所以 ch8 额外引入了 VirtIO-Input 驱动，读 evdev 事件格式（type/code/value），可以准确区分 key-down 和 key-up。

另一个重要的资源限制修改：DOOM 加载 WAD 文件需要大约 4 MiB 内存，而 ch8 的默认用户堆只有几十 KiB，完全不够。为此把用户堆扩大到 8 MiB，用户栈从 2 页增到 16 页，QEMU 内存参数改到 128M，同时调整内核里的物理内存常量。这些不是代码逻辑问题，但如果不做，DOOM 启动时直接因内存分配失败而崩溃。

AI 解释了整条链路的逻辑：用户调用 `framebuffer_flush` → ecall → 内核 syscall 分发 → 把用户 320x200 的 ARGB 帧 2x 放大写到 640x400 GPU 缓冲 → GPU DMA flush → QEMU 窗口显示。这条链路对理解"用户态图形程序如何通过内核访问显示设备"帮助很大。

## 二、学习效果评估

### 知识与能力的变化

四个游戏做下来，最明显的收获在两个方面。

第一是对内核设备驱动的理解。之前"VirtIO GPU"只是一个名字，通过 ch3 实际实现了 VirtIO GPU 驱动之后，理解了 MMIO 基址、DMA 缓冲、HAL 层地址翻译、帧格式转换这一整条链路。到了 ch8 做 VirtIO-Input 时，因为模式已经熟悉了，上手快了很多。同时，因为各种魔改gpu也了解了这玩意到底应该怎么跑才能正确的跑起来（一开始初始化这个驱动的时候全都是报错，后面可以复用了就舒服很多）

第二是对用户态与内核态协作方式的理解。四个游戏都走"内核持有设备资源，用户态通过 syscall 请求服务"的模式。从设计四个绘图 syscall 到后来加 mailbox、最后加 framebuffer/input，每一次都需要判断接口边界在哪里、哪些东西放用户态、哪些放内核。这个判断能力通过反复实践有了明显提升。

### 与本校现有实验教程的对比

正常的实验通常以补全 syscall 和进程管理功能为主，没有"在内核上跑游戏"这类应用导向的实验。这两类实验的侧重点不一样：补 syscall 更侧重理解调用机制和接口语义，而游戏实验更侧重理解"内核能力如何被实际使用"。

游戏实验有一个很直接的优势：验证结果非常直观，窗口显示出来就是通了，画面乱了就是某个环节出问题了，不需要像跑单元测试那样去解读输出。这种即时反馈对调试效率很有帮助。

局限是游戏实验的工程量比较大，特别是驱动移植和构建链适配部分，耗时不少但与操作系统核心原理的关联不是最直接的。如果要更好地融入课程体系，可以考虑把驱动部分预置好，让同学更聚焦在进程协作（pipe、signal、fork）这类章节主题上。

同时由于加入了渲染支持，在图形化方面某些情况下会很麻烦，尤其是在对齐效果方面，但是同时完成也会有较高的成就感。
