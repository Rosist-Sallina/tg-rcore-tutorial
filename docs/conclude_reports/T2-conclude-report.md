# 任务二：个性化实验教程设计总结报告

我们完成了两个个性化实验教程的设计与实现：T2L6（虚拟内存算法教程章节 ch9）和 T2L10（ch3~ch5 多核扩展教程）。

## 实验一：T2L6 虚拟内存管理算法（ch9）

### 设计思路与目标

对纯概念型的虚拟内存讲授有一个感受：教材讲了 FIFO、Clock、LRU，但"什么叫缺页发生了"、"置换到底换了什么"、"为什么抖动"，这些到了要动手的时候都是模糊的。这个方向可以把它做成一个能跑起来的实验来填补空缺。

最开始的想法是直接给出一个完整的 ch9，四个算法全部实现，交给同学运行观察。但和 AI 讨论过后，意识到这样更像是"提供参考答案"而不是"做教程"。最后确定的方向是：保留完整的框架、测例和统计输出协议，只在 `process.rs` 里的懒分配方法（`mmap_lazy`、`handle_page_fault`）和 `pager.rs` 里的 victim 选择逻辑（`pick_fifo_index`、`pick_clock_index`）留 TODO。LRU-approx、Working Set 和抖动检测作为扩展题，不作为最小通过要求。

教学基底固定在 ch4 递进，不挂到 ch8 后面，以便把注意力集中在虚存算法主线上。

### 与 AI 合作的实现过程

这个实验全程使用 Codex CLI（GPT-5.4-XHigh）。

一开始说"帮我做虚拟内存管理算法实验"，AI 先读了仓库里 ch4 的现有实现，发现当前只有"预映射 + 非法 trap 直接杀进程"，完全没有缺页恢复路径。这一步帮我在动手之前先把基线确认清楚，避免在一个"根本不支持缺页"的基础上去设计实验。

然后告诉 AI 目标不是在 ch4 里塞功能点，而是做一整章风格和 ch1~ch8 一致的教程章节。AI 给出了完整的 ch9 设计方案：章节目录、README 内容结构、exercise.md 的任务拆分、syscall 定义（vmctl/VmStats）、pager 子系统设计，以及用户态 benchmark 的格式（四种访存模式：顺序扫描、随机访问、强局部性、弱局部性）。方案定好后直接让 AI 实现。

这个阶段遇到的主要问题有两类。第一类是依赖名不匹配：这个仓库的学生版 crate 包名和上游官方包名不一样，AI 在第一轮实现里用了官方包名，导致构建链解析失败。定位后改成仓库里实际的学生版包名才通。这是这个仓库里反复出现的环境问题。

第二类是 Rust 的借用冲突和调度栈溢出。pager 的 `fault_in_page` 函数里需要先读出页状态再回写，如果直接在 match 里做，Rust 报"在持有不可变引用的同时试图可变修改同一 map"的错误，解法是先 clone 枚举值出来，离开 match 作用域后再写入。另一个问题是 `vm_bench` 的调度栈溢出——`schedule -> pager -> log/format` 的调用深度比普通 ch4 深，2 页内核调度栈不够用，加厚后解决。

还有一个 thrashing 告警频率问题：算法跑对了，但日志里 thrashing 事件每秒几百条，benchmark 输出完全淹没在告警里。AI 改成"计数照常，日志只打前几次"，不影响统计数据。

最后把 ch9 改成"教程练习版"：默认 `cargo build` 通过，`--features exercise` 也能编过但运行时在 TODO 处停住，这是真正可以发给同学做的版本。

### 学习效果评估

这个实验最大的收获不是某个算法本身，而是"如何把原理性内容设计成可实验的形式"这个过程。通过实际实现，理解了：缺页处理的合法/非法判断需要提前登记可分页区间，不能在 trap 时才去猜；A/D 位的维护是置换算法的数据基础，如果不定时扫描和清零，Clock 和 LRU-approx 的统计就是无效的；抖动检测的核心是窗口内 fault rate 和 eviction rate 的比例关系，不是算法复杂度。

与本校现有教程的对比：本校课程里虚拟内存通常以理论讲授为主，没有对应的"可运行、可比较"的实验。这次设计的 ch9 补了一个缺口：让同学能跑出"顺序扫描下 FIFO 表现如何、强局部性访问下 Clock 和 LRU-approx 的差距是多少、什么样的访存模式会触发抖动"这类可量化的数据。局限在于：这次用进程级配额模拟受限物理内存，不是真正的多进程竞争物理内存的场景。


## 实验二：T2L10 ch3~ch5 多核扩展教程

### 设计思路与目标

ch3~ch5 原本完全是单核设计：没有任何 SMP 相关代码，QEMU 启动无 `-smp` 参数，所有同步依赖 `UPIntrFreeCell`（单核中断屏蔽），全局状态通过 `UnsafeCell` 访问（单核安全，多核不安全）。多核是操作系统最容易出 bug 的部分之一，设计这个实验的目标就是让同学通过逐层适配，真正理解"单核代码在多核下为什么会炸"。

三种方案对比之后，选了"自底向上渐进式"：先构建共享的 SMP 基础设施 crate，再逐章节适配，每步可独立验证。这和 tg-rcore-tutorial 本身的渐进式风格一致，也让同学能清楚看到每层抽象的职责。

具体结构是：新增 `tg-rcore-tutorial-smp` crate（提供 SpinLock、PerCpu、hart 启动、内存屏障、IPI）；升级 `tg-rcore-tutorial-sync`（保留 `UPIntrFreeCell` 接口，但在 `smp` feature 下切换成 `SpinNoIrq` 内部实现）；再依次做 ch3、ch4、ch5 的多核适配。

### 与 AI 合作的实现过程

这个实验使用 Claude Code（Claude Opus 4.6）。

整个过程中最关键也最花时间的不是调度算法，而是运行环境的基线问题。

最开始打算走 `-bios none`（仓库自带的最小 SBI），想在里面补 HSM 支持来启动副核。实现了 HSM ecall handler，HSM 本身能返回了，但副核始终没有进入 S 模式。排查了很长时间，最终发现问题出在"停车等待"的实现逻辑里：副核在 M-mode 中先检查状态位再决定是否 WFI，但我的实现是先 WFI 再检查，把副核自己睡死了。修好这个逻辑后，副核能起来了，但又遇到了新的问题：`ch3/ch4/ch5` 的链接脚本把内核链接在 `0x80000000`，和真正完整的 OpenSBI 固件重叠。

最后做了一个关键决定：放弃在最小 SBI 里补 HSM，直接改成让 QEMU 使用默认 OpenSBI。理由很直接：教学最小 SBI 只适合单核，真正多核需要可靠的 HSM / IPI 语义，直接用 OpenSBI 可以把副核启动稳定下来，调试成本更低。对应地把三章的 build.rs 改成普通链接脚本，`.cargo/config.toml` 里加 `-smp 2`。

环境基线稳定后，主要的实现问题集中在三类：

第一类：主核不一定是 hart 0。OpenSBI 的 boot hart 在 QEMU 里不保证是 0，有时候 hart 1 先进来。所以不能写死"主核固定为 0、副核固定为 1"，改成`current = hart::hart_id()`，`other = 1 - current` 来动态判断。

第二类：单核 `current` 语义在多核下失效。ch5 原来的 `PROCESSOR.current()` 默认只有一份。多核下每核需要独立的"当前进程"指针，改成 PerCpu 存储后才对。

第三类：OpenSBI 的 `console_getchar()` 没有输入时返回 `-1`，shell 的 `read` 如果直接把返回值转 `u8`，会把 `0xff` 一路喂进用户态，最后把 shell 自己喂爆。修法是把 `read` 改成真正的阻塞读：`console_getchar` 返回负值时继续等，不往上层传。

最终运行结果：ch3 双核能稳定跑用户程序；ch4 副核能激活页表并进入调度；ch5 能进 `Rust user shell`，稳定出现 `>>`。

### 学习效果评估

这个实验让我对"单核和多核的本质区别"有了比之前清晰得多的认识。

之前理解是"多核就是多个 CPU 同时跑"，但通过这次实验，真正理解了几个更细的层次：`UPIntrFreeCell` 靠关中断保证临界区安全，但关中断只能阻止当前核被打断，无法阻止其他核同时访问同一数据——这就是为什么多核下必须换 SpinLock；TLB shootdown 在 ch4 里的必要性，即一核 `munmap` 后其他核可能还拿着旧的 TLB 翻译，这是一类在单核下完全不会暴露的 bug；ch5 的 `fork/wait/exit` 在多核下的父子进程状态同步问题，本质上是"进程表的并发修改需要全局锁"。

与本校现有教程的对比：多核方向的内容在现有课程里几乎是空白，大部分实验假设单核运行。这次实验通过"把单核代码逐步适配到多核"的方式，把单核设计的隐含假设一条一条暴露出来，每次暴露都是一次具体的教学点。这种方式比直接讲"多核编程注意事项"更有说服力，因为同学能亲眼看到"什么样的代码在单核下没问题、在多核下就炸了"。
