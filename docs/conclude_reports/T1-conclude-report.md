# 任务一：基础实验实践总结报告

## 一、与 AI 合作的实现过程

### 总体交互策略

在完成五个基础实验（ch3/ch4/ch5/ch6/ch8）的过程中，我使用的是 Codex CLI（GPT-5.4-xhigh）.每个章节开始时先向 AI 索取完整的实现框架和思路，自己动手尝试后遇到具体问题再追问。这样做的目的是让自己真正理解每一步在做什么，而不是把代码粘贴过来运行了事。


### ch3：多任务内核中的 sys_trace 实现

这一章的核心任务是在多任务内核上补充 sys_trace，支持读字节、写字节、查询 syscall 调用次数三种行为。

一开始我让 AI 给出完整的实现路线，AI 把整个任务拆成了七步，从调用链分析到 TCB 中怎么存 syscall 统计表，到 TRACE 在哪里拦截，都讲得比较清楚。按这个框架自己实现后，遇到了一个比较典型的 bug：`count_syscall(SYS_TRACE)` 查询结果始终比预期少 1。

追问 AI 后，它让我检查 `handle_syscall()` 里计数和分发的顺序。发现问题出在"先走分发逻辑、再记计数"，而题目要求"本次 trace 调用本身也要计入"，所以计数必须放在任何分发之前。调整顺序后问题消失。

这个 bug 的原因很简单，但如果没有这个提示，我可能会在别的地方找很久。顺带也确认了 `main.rs` 里的 `impl Trace for SyscallContext` 占位实现不影响正确性，因为 TRACE 在 TCB 层已经被本地拦截掉了，根本不会走到那里。


### ch4：地址空间内核中的 trace / mmap / munmap

这章要把 ch3 的 syscall 统计迁到 Process，同时用页表翻译重写 trace，再新增 mmap 和 munmap。

AI 给的框架是按顺序来做：先迁移统计，再改 trace，最后做 mmap 和 munmap。最核心的变化是 ch4 不能再直接用裸指针读写用户地址，必须先通过页表翻译再访问。

实现过程中遇到了一个 Rust 借用冲突：在 `main.rs` 里同时持有 `process.context` 的可变借用和对 `process.record_syscall()` 的调用，编译器直接报错。AI 的建议是把需要从寄存器里读的值提前拎成局部变量，让第一个借用尽早结束，再去调 `record_syscall`，最后再重新借用写回返回值。这个解法很直接，但如果对 Rust 借用规则不熟悉的话确实很容易卡在这里。

另外有一次运行时看到 `LoadPageFault @ 0x10000000`，不确定是不是自己的问题。AI 分析说这个地址和报错类型对应的是"有意给错权限的测例"（只给写权限，然后去读），属于预期行为，不是 bug。这个判断帮我省了一些不必要的排查时间。

### ch5：进程管理扩展——spawn 与 stride 调度

这章要做三件事：把 mmap/munmap 前向兼容进来，实现 spawn，再实现 stride 调度和 set_priority。

mmap/munmap 的前向兼容部分基本就是把 ch4 的代码迁过来适配，AI 直接协助完成了，测例通过。

spawn 的实现花了更多时间。AI 提示说这题真正的难点不是 syscall 语义，而是 Rust 借用顺序：需要先在内层作用域里完成"解析路径 + 构造子进程 + 取出 parent_pid"，等借用结束后再去调 `PROCESSOR.add()`，不然会出现"还拿着当前进程的可变借用，又去借用整个 processor"的冲突。

实现过程中还遇到了一个类型名冲突：`.and_then(Process::from_elf)` 处编译器提示用 `dyn` 关键字。AI 解释这是因为文件里同时存在自己的结构体 `crate::process::Process` 和 syscall trait `tg_syscall::Process`，编译器把 `Process` 解析成了 trait 而不是结构体。改用全路径就解决了。

stride 更新时机也专门确认了一遍。AI 的答案是放在 `fetch()` 里，也就是进程真正被选中执行的那一刻，而不是 `add()`、`set_priority()` 或 `spawn()` 里。这个时机直接影响调度公平性，不能随意放。

### ch6：文件系统扩展——linkat / unlinkat / fstat

这章除了把 ch5 的能力前向兼容进来，主要是在 easy-fs 里增加硬链接支持：给 DiskInode 加 nlink 字段，实现 inode 引用计数回收，以及三个新 syscall。

AI 把这章拆成了四层来实现：磁盘元数据层（nlink）、资源回收层、目录项逻辑层、syscall 层，顺序很清晰。

中间询问了 `inode_id` 是什么，AI 用"身份证号"来类比：name 是目录里的名字，inode_id 是名字指向的文件本体的编号，fd 是进程打开文件时拿到的句柄，block_id 是更底层的磁盘块。硬链接的本质就是"两个不同名字指向同一个 inode_id"。这个类比让我对硬链接的实现思路一下子清楚了很多。

也询问了 `.lock()` 的作用。AI 解释了 `Arc<Mutex<T>>` 的用法：文件系统这些全局共享结构不能同时被多个执行流修改，`.lock()` 是申请互斥访问，guard 离开作用域后自动释放。对这个模式之前只是知道有，通过这次解释算是真正理解了。

实现完成后让 AI 做了一次 code review，它指出了三个问题：unlink 时的目录项删除策略（应该写空槽而不是缩 size，否则目录 inode 的数据块会泄漏）；`read_user_cstr` 只翻译第一页存在跨页安全问题；文件名长度需要在入口处就拒绝，不能留到 `DirEntry::new` 里才 panic。这些超出了最低通过要求，但属于真实工程中确实会出问题的地方。

### ch8：线程与死锁检测

这章要在现有的线程和同步原语框架上加一个"按进程开关的死锁检测"功能。

AI 首先明确了一个设计判断：检测状态不应该放在 `tg-sync` 公共库里，因为公共库不了解进程级的资源持有情况，应该放在 `ch8/src/process.rs` 的进程共享状态中。这个判断让我理解了"状态应该放在哪一层"这个设计问题的思考方式。

框架分四块：进程级检测状态、mutex 检测（同一线程二次锁定自己已持有的锁直接返回 -0xDEAD）、semaphore 的银行家算法检测（Allocation/Need/Available 三张表）、以及 enable_deadlock_detect 开关。

实现过程中发现自己的死锁检测循环没有正确的退出条件，可能导致无限循环。AI 把这个称为"硬伤"。修复后继续推进。

构建时还出现了另一个问题：ch8 的 Cargo.toml 依赖了旧版 easy-fs 的包名，导致编译失败。AI 协助改正了包名引用，同时把 `tg-syscall/src/user.rs` 里的 `asm!` 包进显式 `unsafe {}` 以兼容 Rust 2024 工具链。

最终三个死锁测例全部通过，`ch8 Usertests passed!`。

## 二、学习效果评估

### 知识与能力的变化

这五章走下来，感受最深的是 Rust 在系统编程场景下的借用规则。ch4 和 ch5 里接连遇到的借用冲突，让我对"何时需要提前提取局部变量""如何控制借用的生命周期范围"有了更实际的感受。之前只是理论上知道 Rust 有严格的借用检查，但真正写内核代码时才体会到这些规则的存在感有多强。

文件系统部分（ch6）对 inode/name/fd/block 四层抽象的理解比之前清晰了很多。之前读教材时这些概念是孤立的，实际实现硬链接之后，"多个名字共享同一个 inode"就变成了一个具体的操作，而不只是一句描述。

死锁检测（ch8）是五章里对我来说收获最大的部分。银行家算法在教材里学过，但真正把 Allocation/Need/Available 三张表落到代码里、确定更新时机，还是需要相当多的思考。这章的实现让我对"理论上知道"和"能写出来"之间的差距有了更直接的认识。

### 与本校现有实验教程的对比

很多其他课程的实验通常是"填空式"：给定代码框架，补全几个关键函数，能跑通测例就算完成。这种方式对建立初步信心很有帮助，但遇到真正的 bug 时往往没有足够的上下文去理解为什么。

这次 AI 协作的方式更像是随时可以找一个熟悉这套代码的人问问题。最明显的区别是在 bug 定位上：ch3 的 off-by-one 错误、ch4 的借用冲突、ch5 的类型名冲突，在传统实验模式下可能需要等助教答疑或者在论坛上发帖，这次基本都在几轮对话内找到了根因。

当然这种方式也有明显的局限。ch5 和 ch6 的前向兼容部分是让 AI 直接协助完成的，这部分的理解深度明显不如自己动手的部分。另外 AI 判断"测例通过了"有时只是基于运行日志，ch6 里那三个安全性问题（目录项泄漏、跨页指针、文件名长度）如果不是主动要求 code review，大概率不会被发现。

总体来说，AI 作为学习辅助工具在"解释概念""定位 bug 根因""指出改进空间"这三件事上价值明显，但要真正学到东西，还是需要自己先动手、遇到问题再问，而不是一开始就把代码生成出来。
